# Bounded sequence and stop gates

**No production work is authorized by WP7.4.1.** This recommendation refines
[WP7.4 slicing](../wp7-4/IMPLEMENTATION-SLICES.md) and the new requirement.
Approve mechanisms independently, then start a separately named package.

## Recommendation and challenge to a simple linear rollout

An **unwired pure evaluator first** is safe and useful: hand examples can
settle floor/hold/result semantics without a file change. An Actual Start or
format6 feature enabled immediately afterwards is **not** safe by itself.
The current Save/import/task/calendar/inline paths and PA/FF/CPM labels would
still bypass or misdescribe new commitments. Thus foundation can be developed
second, but public activation waits for the coordinator, all edit gates,
reference labels and lifecycle guard. Do not ship a partially interpreted v6.

Alternative: implement persistence first as WP7.4 proposed. This is reasonable
for an internal foundation but cannot resolve P01 arithmetic by itself and
adds a wider version/recovery surface before owner decisions. Recommend the
pure-first path below, with an explicit dormant-foundation gate. Do not bundle
all layers into one authorization just because they have integration dependencies.

WP7.4.2 is a proposed **next name/scope**, not an instruction to start it.
P09/P11 full integration can remain deferred while an approved pure unused
module is built; it may not consume/produce persisted v6. The foundation and
activation must each be separately authorized after resolving their policies.

## First-slice exact acceptance

1. Input/output interface and bound kinds match [P12](P12-CONSUMER-CONTRACT.md).
   Floors and holds remain distinct from calculated start; no direct graph or
   status decision inside the evaluator.
2. All literal [C01-C12](P01-CALCULATED-COMMITMENT.md) answers, E13-E18 and
   read-only completion/readiness invariants pass independently. Durable
   completion-context capture tests belong to the later coordinator, not this
   pure module. No expected output
   generated by the function under test. Validate dates/graph/range, unknown
   ancestors, future facts, recorded conflicts, ties and permutation determinism.
3. Deeply frozen/serialized inputs compare unchanged: baseline, current W,
   source tasks/events and independent effort remain intact. No new actual
   start, finish hour, remaining-slot conversion or release from reopened history.
4. Current `npm.cmd run check` and relevant/full existing browser regressions
   pass. Report actual counts, not this design's historical counts. Demonstrate
   zero import/use by App/production consumers and zero persistence/config diff.
5. Benchmark30/40-task sparse/diamond/long-chain inputs with explicit environment
   and p50/p95/max/long-task interpretation. Do not assert classroom-device or
   UI readiness from Node timings. No path/day enumeration or repeated state loop.

## Integration risks and stop conditions

- If a pure first slice needs an App setter, public format dispatch or a changed
  calculation to test itself, stop and request a differently scoped package.
- If exact started/reopened finish is requested, Actual Start is insufficient;
  design separate remaining scheduled duration/restart evidence first.
- If P09 fails on a target browser, fail closed; do not invent an unlocked
  fallback. Another backend/guarantee needs an approved contract.
- If P11 guard/history retention is rejected, retain v6 deletion disabled until
  another explicit safe lifecycle is approved; do not purge new evidence.
- If owner requires W-aware PA/FF/CPM, scope that algorithm/reference change
  separately. Current rules stay unchanged in this first slice.

No main merge, tags, deployment, resource levelling, mandatory logs, new status,
actual-hour capture, automatic effort decrement, rebaseline, full archival,
projected backward CPM, remote sync, WP8 or broad chart enhancement is included.
