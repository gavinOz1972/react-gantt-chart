# Future HTTP/DBMS adapter sketch - no endpoints or schema implemented

Accepted direction: multiple students may later edit a shared project through
an API/relational DBMS. Current scope designs whole-project optimistic concurrency
only. No authentication, presence, automatic merge, WebSocket, SQL/DDL, endpoint
or live collaboration implementation is included.

## One semantic contract, different transport/physical representation

The HTTP adapter implements [ProjectRepository](REPOSITORY-CONTRACT.md) and maps
its typed results, not file import/export or domain scheduling. A future server
loads/assembles a validated normalized snapshot; a relational mapping may store
tasks, ordered evidence, working commitments, baseline and receipt information
separately. The server's repository unit of work persists their complete accepted
revision and receipt atomically. No requirement to store one JSON blob, browser
key layout, lock name or library cap. Physical normalization/DBMS choice remains
deferred; no table design is selected here.

Preserve array sequence explicitly when reconstructing evidence/history; do
not rely on unordered rows or sort by effective date. Preserve opaque baseline
extras, exact IDs/strings, missing/null and numeric precision. Cross-language
canonicalization golden vectors must match before claiming substitutability.
An immutable baseline JSON artifact can coexist with other normalized entities;
it need not be regenerated by a new scheduling algorithm.

## Illustrative request/response profile

These paths/media types are examples for owner review, not reserved endpoints:

```http
GET /api/projects/r-7/revision
Accept: application/vnd.bugsys.project-snapshot+json;version=1

200 OK
ETag: "r17-<semantic-fingerprint>"
Content-Type: application/vnd.bugsys.project-snapshot+json;version=1

{ "modelVersion": 1, "logicalRevision": 17, "state": "...", "history": ["..."] }
```

The GET representation would be canonical snapshot bytes; its strong validator
is derived from that state/ref, not an independent row counter. A conditional
write maps the port's expected ref and immutable transaction ID:

```http
PUT /api/projects/r-7/revision
If-Match: "r17-<semantic-fingerprint>"
Idempotency-Key: tx-18
Content-Type: application/vnd.bugsys.project-snapshot+json;version=1

{ "modelVersion": 1, "logicalRevision": 18,
  "state": "complete candidate, including completion/graph/Unresolved",
  "history": ["unchanged groups", "group18 containing tx-18 operations"] }

200 OK
Content-Type: application/json

{ "kind": "Committed", "receipt": { "projectId": "r-7",
  "transactionId": "tx-18", "committedRef": { "revision": 18,
  "fingerprint": "<new fingerprint>" } }, "currentRef": "same ref" }
```

Receipt responses need not advertise a new representation validator; load the
snapshot when reconciliation needs it. A retry after a later revision may return
AlreadyCommitted with receipt18/currentRef20. The client must not publish an
old revision18 candidate as though it were current20.

Create/Save As can use `POST /api/projects` with Idempotency-Key and label plus
complete snapshot. New resource ID is server-assigned; importing17 keeps logical17.
Same create key/intent returns its original resource, different intent conflicts.
Names do not confer identity or permission. List pagination is discovery, not
an atomic multi-project view. These behaviors must match the browser profile.

The [HTTP semantics specification, If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)
defines conditional state changes using strong validators and describes failed
preconditions/known prior success. This supports using a conditional write to
avoid lost updates; the exact idempotency ledger/profile above is our proposed
application contract, not a claim that HTTP alone provides its transaction.

## Server-owned decision boundary

Conceptual unit of work, not executable SQL:

```text
authenticate/authorize caller for repository namespace and target resource
begin backend transaction
  find target; examine transaction receipt for this authorized scope
  if exact prior intent: return original receipt + current ref
  if reused ID/different intent: reject conflict
  compare expected revision/fingerprint with accepted snapshot
  validate full candidate, next revision, baseline/known lineage, append-only data
  persist normalized accepted entities + new revision + receipt together
commit backend transaction
return acceptance; client publishes only after known result/reconciliation
```

A client-supplied user/actor label is not authorization. The server owns access
policy, expected-ref comparison and invariant enforcement; a client validator
or TypeScript brand is not trusted. Known-lineage first-baseline adoption must
be serialized/validated with resource creation and commits, not a racy global
check followed by an unrelated write. No cross-project editing API follows.

Suggested mapping:404 -> NotFound (as policy permits),412 -> StaleRevision
Conflict,409 -> TransactionIdReuse,422 -> Validation, unsupported profile ->
Unsupported. Future401/403 maps AccessDenied; details/credential mechanism are
deferred. A server-confirmed rollback can be StorageFailure(NotCommitted);
an ambiguous timeout/network break is OutcomeUnknown, not definitely unsaved.
HTTP status alone cannot prove a received write did not commit after connection
loss. Preserve exact same request for receipt reconciliation.

## Deliberately deferred collaboration choices

Whole-project revision means concurrent edits to different tasks still conflict.
No automatic rebase, task-level merge, CRDT/operational transform, server push,
presence, websocket channel, pessimistic locking UI, task assignment or role
design. Future authorization/session/tenant ownership, audit authentication,
conflict-resolution UX, database schema/indexes/isolation, receipt retention
operations and API availability guarantees need separate packages.

Reusable now: pure WP1/working/progress rules, immutable baseline semantics,
normalized snapshot/ref, whole-project CAS, idempotency and typed failure tests,
portable codec boundary and accepted-state publication rule. Not reusable as
shared semantics: local key names, whole-library byte cap, Web Locks, browser
origin quota or copy-name lookup. Future adapter must pass the same semantic
suite, with native server/DB transaction tests; the memory examples certify none.
